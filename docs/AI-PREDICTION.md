# AI Demand Prediction

**Status:** Implemented (Day 2) · **Endpoint:** `GET /api/analytics/demand-forecast/`
**Code:** `backend/analytics/forecasting.py` · **Tests:** `backend/analytics/tests.py` (33 tests, all passing)

---

## 1. Read this first: the data is synthetic

> **The demand forecast is fitted on a generated dataset, not on real customer orders.**
> Every API response carries `"is_synthetic": true` and a `provenance_note`. The admin UI shows a warning banner. Nothing in this feature should ever be presented as real observed demand.

### Why

The real database contains:

| Metric | Value |
|---|---|
| Orders | **8** |
| Order items | **20** |
| Distinct products ever sold | **5** |
| Distinct order days | **9** (non-consecutive) |
| Date of most recent order | ~5 months before the model was built |

You cannot train a seasonal demand model on 8 orders. A model fitted to that would produce confident-looking numbers with no predictive content — which is precisely the *"fake AI"* the brief forbids.

### The approach taken

Rather than ship a fake model or no model, the pipeline is **real** and the data is **openly labelled**:

- A genuine, evaluable forecasting model (`SeasonalForecaster`).
- Trained on a synthetic dataset written to its own table with a per-row `is_synthetic` flag.
- Evaluated with a **real out-of-sample metric** (MAPE) on a held-out tail.
- Swapping in real data later requires **no model change** — only a different data source.

This is the difference between *"we built a forecasting pipeline over labelled synthetic data"* (true, verifiable, useful) and *"we predict demand"* (false).

## 2. The synthetic dataset

Generated by `python manage.py generate_synthetic_sales` (`--purge` to rebuild).

| Property | Value |
|---|---|
| Rows | **14,000** |
| Products | 35 |
| Days | **400** (~13 months, full annual cycle) |
| Date range | 2025-08-01 → 2025-09-… |
| Seed | `20260918` — **fixed, so regeneration is byte-identical** |
| Table | `analytics.SyntheticSalesRecord` |
| Rows tagged with a festival | 3,640 |
| Storage | Separate table — real orders are never mixed with fabricated rows |

### What the generator injects

The generated world contains four structures that a naive model would fail to capture. They are the *ground truth the model must recover*:

1. **An annual festival cycle** — demand ramps toward Dashain (×4.0), Tihar (×3.2), Shivaratri (×2.6), Teej (×2.2), Chhath (×2.0).
2. **Day-of-week seasonality** — Saturday (the Nepali weekly holiday) is highest at 1.30; Tuesday is lowest at 0.90.
3. **A mild per-product trend** — slope drawn uniformly from `[-0.0016, +0.0022]` per day.
4. **Poisson-ish noise** — Gaussian jitter (σ = 0.18) on a rounded expectation, so series are integers with realistic variance.

Base daily demand is anchored to each product's real `popularity_score` (`0.6 + score/100 × 3.4` units/day), so the synthetic catalogue has the same shape as the real one.

## 3. The model

**Multiplicative seasonal-trend decomposition with a festival calendar term.**

```
forecast(d) = level × weekday_factor(d) × festival_factor(d) × trend(d)
```

| Term | How it is derived | Why |
|---|---|---|
| **level** | Median of the festival-adjusted series | Median, not mean: a single Dashain spike would otherwise inflate the baseline for the whole year |
| **weekday_factor** | Mean of festival-adjusted values per weekday, ÷ overall mean | Captures the Saturday holiday effect |
| **festival_factor** | Linear ramp to ×2.4 over 21 days before a festival; ×0.35 damping for 4 days after | The calendar is the dominant driver in this domain |
| **trend** | Least-squares slope on the adjusted series, then **×0.5 damping** | Damping prevents a 90-day forecast from running away |

All factors are clamped (`weekday ∈ [0.55, 1.65]`, `trend ∈ [0.75, 1.35]`) so one anomalous week cannot produce an absurd forecast. There is a test that injects a 1000× spike and asserts the clamp holds.

### Why hand-written rather than scikit-learn

Adding `scikit-learn` + `numpy` + `scipy` means roughly 60 MB of dependencies for a model whose dataset, until real volume exists, is 8 orders. The brief explicitly forbids unnecessary dependencies. The decomposition above is ~200 lines of stdlib Python and is fully explainable to a non-ML reviewer — which matters more here than marginal accuracy.

## 4. Does it actually work?

Yes, and this is verifiable. Evaluation is a **holdout**: fit on all but the last 28 days, then predict those days and compare against actuals the model never saw.

### Headline numbers (35 products, 28-day holdout)

| Metric | Value |
|---|---|
| Mean MAPE | **26.20 %** |
| Median MAPE | 25.98 % |
| Best / worst product MAPE | 12.49 % / 51.62 % |
| Mean MAE (model) | **0.810 units** |
| Mean MAE (naive: predict training mean) | 0.936 units |
| **Improvement over naive baseline** | **+13.5 %** |

### The model recovered structure it was never told about

This is the strongest evidence it is a real model. Compare the weekday factors **the model learned** against the generator's hidden ground truth:

| Day | Generator's truth | Model learned | |
|---|---|---|---|
| Tuesday | 0.90 | **0.842** | lowest ✓ |
| Wednesday | 0.98 | 0.917 | |
| Monday | 0.95 | 0.884 | |
| Sunday | 1.10 | 1.059 | |
| Friday | 1.15 | **1.094** | 2nd highest ✓ |
| Saturday | 1.30 | **1.191** | **highest ✓** |

The model independently rediscovered the Saturday holiday spike and the Tuesday trough purely from the data. `test_learns_saturday_spike` and `test_beats_naive_baseline_out_of_sample` assert this.

### Honest assessment

**26.2 % MAPE is mediocre.** For context, good retail demand forecasts land in the 10–20 % range. This is expected: the series are low-count integers (0–5 units/day), where rounding alone contributes large percentage error, and the 28-day holdout sits in a festive period the model has to extrapolate into. We report it as-is rather than quoting a flattering in-sample number.

## 5. API

### `GET /api/analytics/demand-forecast/`

**Auth:** `IsAdminUser` — verified 403 for customers, 401 for anonymous.

| Param | Default | Range |
|---|---|---|
| `horizon` | 30 | 1–90 (clamped) |
| `limit` | 12 | 1–50 (clamped) |
| `product` | — | integer id; non-integer → `400` |

```jsonc
{
  "data_source": "synthetic",
  "is_synthetic": true,
  "provenance_note": "SYNTHETIC DATA: this forecast is fitted on a generated dataset...",
  "horizon_days": 30,
  "forecasts": [
    {
      "product": { "id": 18, "name": "Dried Coconut (Nariwal)", "category": "Offerings & Prasad", "price": 60.0, "stock": 150 },

      "stock_cover_days": 11.1,
      "restock_needed": true,
      "projected_shortfall": 257.0,
      "metrics": { "holdout_days": 28, "mape": 16.52, "mae": 2.1, "rmse": 2.6, "note": "..." },
      "components": {
        "level": 5.0,
        "weekday_factors": { "Mon": 0.884, "Tue": 0.842, "Sat": 1.191, ... },
        "trend_slope_per_day": 0.00023,
        "train_days": 400
      },
      "predictions": [ { "date": "2026-09-18", "units": 12.4, "festival": null }, ... ]
    }
  ],
  "aggregate": {
    "total_forecast_units": 5943.5,
    "products_covered": 35,
    "products_needing_restock": 24,
```

## 6. Admin UI

`admin-dashboard/src/app/forecast/page.js` → nav item **"Demand Forecast"**.

- Warning banner stating the data is synthetic, shown above everything else.
- Four summary cards: forecast demand, products covered, restock count, mean MAPE.
- Sortable table ranked by projected shortfall: stock, forecast, shortfall, days-of-cover, inline SVG sparkline of the predicted series, and an MAPE badge (green <15 %, amber <30 %, red ≥30 %).
- **"Why?" expander** per row: shows the fitted level, trend slope, training days, festival lift, and the full weekday-factor table with ↑/↓ markers. This is the model's own internals, not a mock-up.
- Loading skeletons, error state with retry, and empty state.

The sparkline is hand-rolled SVG rather than a charting library — 30–90 integer points do not justify the dependency.

## 7. Known issues and limitations

- **24 of 35 products flagged for restock is implausibly high.** This is a *data calibration* artifact, not a model bug: the synthetic generator's demand levels exceed the catalogue's seeded stock levels for many products. Real demand would be calibrated against actual sales. Documented rather than tuned away, because tuning it would hide the fact that the synthetic generator's absolute scale is arbitrary.
- **Absolute units are not meaningful.** Only the *shape* (weekly cycle, festival ramp, trend) carries signal. Do not read `406.99 units` as a real figure.
- **Model does not know about stockouts or promotions.** If a product was out of stock, the model reads that as low demand. This would need censored-demand handling on real data.
- **Festival dates are approximate.** `refresh_festivals` uses offsets from today, not an authoritative panchang. Real deployment needs verified lunar dates per year.
- **No per-category or aggregate-level forecast.** Product-level only.
- **Model is refit on every request.** At 14,000 rows this takes ~2–7 s. That is acceptable for an admin page but would need caching at production scale.
- **No prediction intervals.** Point forecasts only; uncertainty is not quantified.
